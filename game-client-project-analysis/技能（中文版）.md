# 游戏客户端项目快速上手

## 目标

建立一个最小且准确的项目心智模型，让开发者能够在陌生的游戏客户端仓库中开始有效工作。

优先缩短“完成第一次修改所需的时间”，而不是追求架构分析的完整性。

当开发者能够回答以下问题时，就应该停止继续扩展分析：

- 如何打开、运行、构建和验证这个项目？
- 程序从哪里开始执行？简要启动流程是什么？
- 最先需要了解的是哪 3–6 个模块？
- 现在应该优先阅读哪 5–10 个文件？
- 一条具有代表性的功能是如何端到端运行的？
- 第一个任务可能需要修改哪些代码？应该如何验证？

## 分析范围

从用户的实际目标出发。

如果用户已经提供了具体任务，就围绕该任务以及项目中最接近的现有实现进行项目导览。

如果用户没有具体任务，则选择一条能够体现项目结构的代表性流程。

默认以只读方式探索。

不能仅仅因为用户要求理解项目或熟悉项目，就修改代码。

当用户明确要求实现某个任务时，应直接利用项目导览阶段获得的结论继续开发，不要重新进行一次全仓库分析。

避免：

- 进行穷尽式架构审计；
- 编写通用框架教程；
- 进行代码质量评审；
- 提出架构重设计建议；
- 逐文件罗列仓库内容。

只有当缺少上下文会阻碍下一步开发时，才继续扩大分析范围。

## 工作流程

### 1. 建立项目基线

扫描以下内容：

- 仓库根目录；
- README；
- 贡献说明；
- 依赖清单；
- 锁文件；
- 项目设置；
- 构建脚本；
- CI 配置；
- 顶层源码结构。

优先使用 `rg --files` 和有针对性的 `rg` 搜索。

跳过：

- 生成目录；
- 构建目录；
- 缓存目录；
- 包含大量第三方代码的目录。

识别：

- 游戏引擎；
- 引擎版本；
- 开发语言；
- 主要依赖；
- 仓库整体结构；
- 要求使用的编辑器或工具链版本；
- 文档中提供的打开、初始化、运行、构建和测试命令；
- 生成代码；
- 内置或复制进仓库的第三方代码；
- Git 子模块；
- 大型资源；
- 不应该随意修改的本地配置；
- 当前存在的阻塞项，例如缺失的文档、依赖、密钥、资源或平台工具。

不要仅仅为了熟悉项目就运行依赖安装器或不受信任的仓库脚本。

如果用户要求初始化或运行项目，应先检查命令，说明可能产生的重要副作用，并且只在用户授予的操作范围内执行。

对于 Unity 项目，优先检查：

- `ProjectSettings/ProjectVersion.txt`
- `Packages/manifest.json`
- `EditorBuildSettings.asset`
- Assembly Definition 文件
- 第一个启用的 Scene
- Bootstrap 启动代码
- `RuntimeInitializeOnLoadMethod`
- 根 `MonoBehaviour` 生命周期入口

对于 Cocos Creator 项目，优先检查：

- `package.json`
- `tsconfig.json`
- 项目配置和 settings 文件
- 启动 Scene
- Bootstrap `Component`
- `onLoad`
- `start`
- 相关的 `.scene`
- 相关的 `.prefab`
- 相关的 `.meta` 引用关系

如果无法解析序列化引用，标记为：

`UNKNOWN / NEED EDITOR INSPECTION`

对于其他游戏客户端项目，应寻找对应的：

- 版本清单；
- 构建入口；
- Scene 或状态根节点；
- 生命周期钩子；
- 资源管线。

### 2. 建立最小架构地图

只追踪项目的关键主干：

`引擎入口 -> Bootstrap 或对象组装根节点 -> 核心服务 -> 第一个主要状态或目标功能`

根据以下因素识别 3–6 个模块：

- 职责；
- 公共 API；
- 初始化边界；
- 依赖边界。

不要只根据文件夹名称判断模块。

对于每个模块，记录：

- 一句话职责说明；
- 入口文件或入口类型；
- 主要依赖。

创建一张 Mermaid 架构图，节点数量控制在大约 10 个以内。

只使用项目中真实存在的符号。

只有当通信方式的区别能够帮助开发者采取行动时，才标记：

- 直接调用；
- 依赖注入；
- 事件；
- 异步响应；
- 引擎生命周期；
- 序列化连接。

### 3. 追踪一条真实功能链

如果用户已经有具体任务，寻找与该任务最接近的现有功能，并追踪这条功能链。

如果用户没有具体任务，则选择一条能够跨越关键层次的流程，例如：

- 从启动到主界面；
- 打开一个页面；
- 加载一个资源；
- 完成一个依赖网络的操作。

追踪：

- 用户、引擎或消息入口；
- Controller、System 或 Component 的编排过程；
- 实际涉及的数据、网络、资源、事件或场景依赖；
- 可见结果；
- 已存在的错误处理流程；
- 会影响代码修改的生命周期、注册、所有权和清理规则。

展示一条简洁的调用链或时序图，并引用一个真实使用示例。

绝不能虚构缺失的：

- 调用者；
- 序列化连接；
- 运行时顺序。

### 4. 提取开发约定

不要搜索整个仓库。

阅读目标功能附近的两到三个具有代表性的现有实现。

只提取下一次修改真正需要的约定：

- 新功能或修改后的功能在哪里注册和初始化；
- 依赖是如何获得的；
- 异步工作如何处理；
- 错误如何处理；
- 事件如何使用；
- 生命周期清理如何完成；
- UI、资源、Scene、协议或配置如何命名和引用；
- 哪些文件是生成文件；
- 生成文件对应的源码或生成器是什么；
- 测试或实际验证代码位于哪里。

区分：

- 项目中重复出现的约定；
- 只出现一次的特殊写法。

如果没有足够证据，不要把代码风格观察结果描述为必须遵守的规则。

### 5. 准备第一次开发操作

如果已经知道具体任务，识别：

- 可能的代码修改位置；
- 推荐实现顺序；
- 可以参考的邻近实现；
- 与任务最相关的最小验证方式。

这些内容只是一份任务地图，不代表已经获得修改代码的权限。

如果尚未确定具体任务，应提供一份能够直接支持开发的阅读顺序，并解释每个文件能够帮助开发者理解什么。

不要为了让报告看起来完整而虚构一个功能需求。

## 证据规则

如果能够获得行号，为重要结论添加：

`relative/path:line`

否则使用：

`relative/path`

优先提供少量高质量证据，不要堆砌大量路径引用。

当不确定性会影响下一步操作时，使用以下标签：

- `CONFIRMED`：由代码或配置直接证明。
- `INFERRED`：由多项线索支持，需要说明推断过程。
- `UNKNOWN / NEED VERIFICATION`：无法从当前仓库证据中确认。
- `UNKNOWN / NEED EDITOR INSPECTION`：序列化状态或编辑器状态无法通过文本安全解析。

在代码或配置确认之前，将 README、名称、注释和目录结构视为线索，而不是最终证据。

区分：

- 项目中已经安装的依赖；
- 运行时真正使用的依赖。

## 默认输出格式

# 项目上手简报

## 1. 从这里开始

说明：

- 这是什么项目；
- 使用的引擎和版本；
- 当前证据是否足够；
- 第一个应该打开的文件。

## 2. 打开、运行和验证

列出已经确认的：

- 工具版本；
- 运行命令；
- 构建命令；
- 验证命令。

区分：

- 文档明确提供的命令；
- 根据代码推断的命令。

列出阻塞项，但不要猜测缺失的密钥或资源内容。

## 3. 最小心智模型

提供一张简洁的 Mermaid 图，以及一个包含 3–6 行的模块表格：

| 模块 | 职责 | 入口 | 依赖 |
|---|---|---|---|

## 4. 关键文件

按照依赖关系提供大约 5–10 个文件的阅读顺序。

用一句话解释每个文件能够帮助开发者理解什么。

## 5. 一条端到端功能链

追踪一条真实功能，包括：

- 简洁调用链或时序图；
- 关键文件；
- 生命周期限制；
- 真实使用示例。

## 6. 如何完成第一次修改

如果已经知道任务，列出：

- 可能的修改位置；
- 可以参考的相邻实现；
- 推荐实现顺序；
- 验证方法。

如果还没有具体任务，则总结能够帮助开发者处理下一张需求单的项目约定。

## 7. 未知事项与阻塞项

只列出会影响以下工作的不确定性：

- 运行项目；
- 完成第一次修改。

同时提供成本最低的下一步验证方法。

保持报告篇幅与项目规模相称。

对于小型仓库，几个段落可能已经足够。

对于任务明确的请求，应省略无关模块，并把目标功能放在整个项目地图的中心位置。

## 停止条件

当以下内容已经足够支持实际行动时，停止继续探索：

- 运行或构建路径；
- 关键架构主干；
- 必须阅读的文件；
- 一条真实功能链；
- 下一次开发操作。

不要仅仅为了让报告显得全面而继续阅读代码。

回复前确认：

- 每一个章节都确实缩短了完成第一次修改所需的时间；
- 重要结论都有证据；
- 未知事项已经明确标记；
- 没有把单纯的分析请求当成修改代码的授权。
