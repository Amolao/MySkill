# ChatGPT 网络故障排查

## 目标

找出 ChatGPT 网络异常的可验证根因，并通过最小、可回滚的改动恢复稳定访问。

不要把刷新页面、切换节点、断开重连、重启代理或重启电脑视为最终修复。这些动作只能作为定位状态缓存、连接池或路由漂移问题的证据。

## 适用症状

- ChatGPT 网页端一直加载、空白、登录循环或频繁显示网络错误。
- 桌面端启动后无限加载、消息发送失败或流式输出中断。
- 网页端和桌面端只有其中一个可用。
- 同一网络中其他网站正常，但 ChatGPT 间歇性异常。
- 出现证书、TLS、WebSocket、代理隧道、DNS 或连接重置错误。
- 刷新、重开客户端、重新连接网络或重启网络工具后暂时恢复。

## 不适用范围

- Plus、Pro、Business 或 Enterprise 订阅与计费问题。
- 登录账号被停用、验证码、组织邀请或权限问题。
- OpenAI API 请求参数、SDK、模型名、密钥或 HTTP 4xx 代码调试。
- 绕过学校、公司、地区或组织实施的访问控制。
- 普通网站或整个互联网均不可用的通用网络故障。

## 总体原则

1. **先排除服务端事故。** 检查 OpenAI 状态页，并记录故障发生的准确时间。
2. **先只读采证。** 默认不修改网络、代理、DNS、证书、浏览器或应用数据。
3. **不假定网络架构。** 不预设用户是否使用代理、VPN、PAC、TUN、企业网关或特定软件。
4. **一次只改变一个变量。** 每次改动后立即复测。
5. **优先最小范围修复。** 不全局关闭防火墙、杀毒、IPv6、TLS 检查或系统安全功能。
6. **所有改动均可回滚。** 修改文件、注册表、网络设置或缓存前先备份并记录原值。
7. **保护秘密。** 不输出代理凭据、订阅地址、Cookie、令牌、认证头、账号信息或完整私有配置。
8. **不固定 OpenAI IP。** CDN 和服务地址可能变化，不向 hosts 写入固定 IP。
9. **不把单次成功当成稳定。** 修复后必须进行多轮测试和实际客户端验证。
10. **遵守组织策略。** 受管设备或企业网络涉及证书、代理和防火墙策略时，不擅自绕过或移除管控。

## 首轮决策树

按以下顺序判断，不要跳步：

1. OpenAI 是否有正在发生的事故。
2. 故障是否只影响一个客户端、一个浏览器配置文件或一个用户账户会话。
3. DNS、TCP 443 和 TLS 是否可达。
4. 系统默认路径、显式代理路径和不同 IP 协议路径是否一致。
5. 是否存在 WebSocket、HTTP/3/QUIC、IPv6、TLS 检查或证书链问题。
6. 是否存在系统代理、PAC、环境变量、TUN 和应用实际网络路径不一致。
7. 是否仅剩客户端缓存、扩展、WebView 或应用进程状态问题。
8. 是否为出口网络、节点、运营商或受管网策略导致的间歇性问题。

## 阶段 0：提取现有信息

先使用用户已经提供的信息，不重复询问。需要补充时，只询问会改变诊断分支的事实：

- 操作系统和版本。
- 网页端、桌面端或两者受影响。
- 具体错误文本或浏览器错误代码。
- 最近一次失败的本地时间。
- 当前网络类型：家庭、移动热点、公司、学校或公共网络。
- 是否使用系统代理、PAC、VPN、TUN、企业安全网关或证书检查；未知时标记为“待自动检测”。
- 故障发生时换到另一网络是否恢复。

## 阶段 1：检查服务状态

访问：

- `https://status.openai.com`

若存在影响 ChatGPT、登录、会话、网页或桌面端的事故：

- 记录事故标题、开始时间、当前状态和受影响组件。
- 暂停本机修复。
- 仅执行不会改变系统的证据采集。
- 若本地现象与事故范围不一致，可以继续收集证据，但不得断言本机配置有问题。

## 阶段 2：建立只读诊断基线

优先运行当前平台对应的脚本：

### Windows

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\collect-chatgpt-network.ps1
powershell -ExecutionPolicy Bypass -File .\scripts\test-chatgpt-connectivity.ps1 -Rounds 5
```

如已知本地 HTTP 或 mixed 代理地址，可附加显式测试：

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\test-chatgpt-connectivity.ps1 `
  -Rounds 5 -Proxy http://127.0.0.1:PORT
```

### macOS / Linux

```bash
bash ./scripts/collect-chatgpt-network.sh
bash ./scripts/test-chatgpt-connectivity.sh --rounds 5
```

如已知显式代理：

```bash
bash ./scripts/test-chatgpt-connectivity.sh \
  --rounds 5 --proxy http://127.0.0.1:PORT
```

脚本结果仅用于形成证据，不自动执行修复。

## 阶段 3：比较客户端与网络路径

建立以下测试矩阵：

| 维度 | 路径 A | 路径 B | 目的 |
|---|---|---|---|
| 客户端 | 网页端 | 桌面端 | 判断是否为单客户端状态 |
| 浏览器 | 普通窗口 | 无痕/新配置文件 | 判断扩展、缓存或策略影响 |
| 网络 | 当前网络 | 手机热点或另一可信网络 | 判断本机与网络边界 |
| 代理 | 系统默认路径 | 已确认的显式代理路径 | 判断代理继承和分流差异 |
| IP | IPv4 | IPv6 | 判断 IPv6 绕行或失败 |
| 传输 | HTTP/1.1/TCP | HTTP/3/QUIC | 判断 UDP 或 QUIC 问题 |

不要一次改变多个维度。例如，不要同时换网络、换浏览器、清缓存和重启代理，否则无法定位根因。

## 阶段 4：系统代理与路由一致性

### Windows

只读检查：

```powershell
Get-ChildItem Env: | Where-Object Name -Match '^(HTTP|HTTPS|ALL|NO)_PROXY$'

Get-ItemProperty 'HKCU:\Software\Microsoft\Windows\CurrentVersion\Internet Settings' |
  Select-Object ProxyEnable,ProxyServer,AutoConfigURL,ProxyOverride

netsh winhttp show proxy

Get-NetAdapter | Where-Object Status -eq 'Up'
Get-DnsClientServerAddress
Get-NetRoute -ErrorAction SilentlyContinue |
  Where-Object DestinationPrefix -in @('0.0.0.0/0','::/0')
```

### macOS

只读检查：

```bash
scutil --proxy
networksetup -listallnetworkservices
route -n get default
scutil --dns
```

### Linux

只读检查：

```bash
env | grep -Ei '^(http|https|all|no)_proxy='
ip route
ip -6 route
resolvectl status 2>/dev/null || cat /etc/resolv.conf
```

比较并验证：

- 系统代理是否启用，地址和端口是否真实监听。
- PAC URL 是否可访问，内容是否仍指向有效代理。
- WinHTTP、系统代理、环境变量和应用代理是否互相冲突。
- TUN 已接管流量时，是否又叠加了另一套系统代理。
- 默认 IPv4 和 IPv6 路由是否经过不同网络接口。
- 浏览器或桌面端是否绕过了预期路径。
- `NO_PROXY` 或代理绕过列表是否错误包含 ChatGPT/OpenAI 域名。

不得仅凭常见端口号猜测代理协议；必须通过配置、监听进程或实际请求确认。

## 阶段 5：DNS 与 hosts

检查关键域名：

- `chatgpt.com`
- `auth.openai.com`
- `ws.chatgpt.com`
- `oaistatic.com`
- `oaiusercontent.com`
- `desktop.chat.openai.com`
- `challenges.cloudflare.com`

### DNS 检查

确认：

- 同一域名多次解析是否稳定。
- 系统 DNS、浏览器安全 DNS和代理内置 DNS 是否返回明显不同的路径。
- 是否同时返回 A 和 AAAA 记录。
- 是否出现私有地址、保留地址、异常 NXDOMAIN 或明显过期结果。
- 使用 Fake-IP 时，代理是否正确接管对应地址，而不是泄漏到直连路由。

### hosts 检查

检查系统 hosts 文件中的 OpenAI、ChatGPT、认证、静态资源和 CDN 相关条目。

若存在固定映射：

1. 先备份 hosts。
2. 仅删除或注释明确与 ChatGPT/OpenAI 冲突的条目。
3. 不修改其他软件或组织管理的条目。
4. 不添加新的固定 IP。

## 阶段 6：TCP、TLS 与证书链

对关键域名检查：

- DNS 是否成功。
- TCP 443 是否连接。
- TLS 握手是否成功。
- 证书主体、颁发者和有效期是否合理。
- 系统时间是否准确。
- 是否出现组织代理、杀毒软件或网关签发的替代证书。

以下 HTTP 状态通常仍能证明网络层已到达远端：

- `200`
- `301` / `302`
- `401`
- `403`
- `404`

网络层失败证据包括：

- DNS 解析失败。
- TCP 超时或拒绝连接。
- 代理隧道建立失败。
- TLS 握手失败、证书名称不匹配或证书链不可信。
- 连接被重置或在固定时间后反复断开。

若受管网络要求 TLS 检查，不要自行移除企业根证书或绕过策略。记录证书颁发者和错误，交由网络管理员针对 OpenAI 公共域名调整策略。

## 阶段 7：WebSocket 与长连接

ChatGPT 的实时交互可能依赖安全 WebSocket。重点检查：

- TCP 443 是否允许 WebSocket Upgrade。
- 代理或网关是否改写 Upgrade/Connection 头。
- 长连接空闲超时是否过短。
- 连接池、NAT 或代理核心是否在一段时间后进入陈旧状态。
- 主站、认证、静态资源和 WebSocket 是否走不同出口。

普通访问 `https://ws.chatgpt.com/` 只能证明部分 DNS/TCP/TLS 可达性，不能代替完整 WebSocket 验证。

完整验证应在浏览器开发者工具或桌面端日志中确认：

- WebSocket 握手完成。
- 连接没有立即关闭。
- 发送消息后流式响应能够持续到结束。

## 阶段 8：IPv6 与 HTTP/3/QUIC

仅在证据显示 IPv4 稳定而 IPv6 失败，或 TCP 稳定而 UDP/QUIC 失败时处理。

优先级：

1. 修复代理或网络工具对 IPv6/UDP 的接管。
2. 让 ChatGPT/OpenAI 域名回退到稳定的 TCP 443 路径。
3. 将浏览器禁用 QUIC 仅作为验证手段。
4. 只有明确证据和用户接受影响时，才考虑更广范围的系统设置变化。

不要默认全局关闭 IPv6，也不要永久修改浏览器实验选项作为第一方案。

## 阶段 9：浏览器端排查

按顺序进行：

1. 使用无痕窗口或新浏览器配置文件测试。
2. 暂停内容拦截、隐私、脚本修改、证书或代理类扩展。
3. 检查浏览器安全 DNS 是否绕过系统或代理 DNS。
4. 在开发者工具 Network 中查找：
   - `ERR_PROXY_CONNECTION_FAILED`
   - `ERR_TUNNEL_CONNECTION_FAILED`
   - `ERR_NAME_NOT_RESOLVED`
   - `ERR_CONNECTION_RESET`
   - TLS/证书错误
   - WebSocket 立即关闭或长时间 pending
5. 仅当无痕正常、普通窗口失败时，清除 ChatGPT/OpenAI 相关站点数据。

不要一开始清除全部浏览器数据或重置整个浏览器。

## 阶段 10：桌面端排查

确认：

- 应用版本是否为当前可用版本。
- 应用是否继承系统代理，还是依赖系统路由/TUN。
- 是否残留多个应用或 WebView 进程。
- 应用防火墙规则是否与浏览器不同。
- 应用日志是否记录 DNS、代理、证书、WebSocket 或连接重置错误。
- 应用启动前后系统代理、监听端口或默认路由是否发生变化。

只有满足以下条件时才处理应用缓存：

- DNS、TCP、TLS 和系统默认路径均正常。
- 网页端稳定可用。
- 桌面端持续失败。

处理方式：

1. 完全退出应用。
2. 确认相关进程结束。
3. 自动定位该平台上的实际应用数据目录。
4. 将缓存子目录重命名为带时间戳的备份，不直接删除整个应用目录。
5. 重启并重新验证。

不要硬编码用户名、安装目录或应用数据路径。

## 根因分类与证据要求

输出修改建议前，至少比较以下假设：

| 根因 | 典型证据 |
|---|---|
| OpenAI 服务事故 | 状态页事件与故障时间和功能一致 |
| 单浏览器配置问题 | 无痕或新配置正常，普通配置失败 |
| 单桌面客户端问题 | 网页稳定，桌面端在相同路径持续失败 |
| 代理端口或 PAC 失效 | 系统配置指向未监听端口或无效 PAC |
| 代理路径不一致 | 浏览器、桌面端、系统与显式代理结果不同 |
| 域名分流不完整 | 主站、认证、静态资源或 WebSocket 出口不同 |
| DNS/Fake-IP 异常 | 解析间歇失败、路径不一致或映射未被接管 |
| IPv6 绕行 | IPv4 稳定，IPv6 超时或走不同出口 |
| QUIC/UDP 异常 | HTTP/1.1 稳定，HTTP/3 路径不稳定 |
| TLS 检查问题 | 替代证书、名称不匹配或链不可信 |
| WebSocket 被关闭 | 握手失败、立即关闭或固定空闲时间断开 |
| 出口网络问题 | 同配置换可信网络稳定，本机路径证据正常 |

使用如下证据表：

| 假设 | 支持证据 | 反证 | 置信度 | 最小修复 |
|---|---|---|---|---|

不得只写“可能是 VPN/代理问题”。

## 修复顺序

### 修复 1：统一 OpenAI 相关流量路径

在实际使用的代理、防火墙、网关或路由配置中：

- 让 ChatGPT 主站、认证、静态资源、文件和 WebSocket 使用一致且稳定的策略。
- 允许 TCP 443 和 WebSocket Upgrade。
- 避免对 OpenAI 公共域名进行内容重写或不兼容的 TLS 解密。
- 不将认证域名与主站分配到不一致出口。
- 使用域名或域名后缀规则，不固定 IP。

必须依据用户实际软件或设备的配置格式生成修改，不假定兼容任何特定代理内核。

### 修复 2：校准代理、PAC 与监听端口

仅在证据明确时：

- 将系统代理改为真实监听且已测试成功的端口。
- 修复或移除失效 PAC。
- 清理指向旧端口的环境变量。
- 避免同时使用互相冲突的系统代理和 TUN 路径。
- 仅在确认影响目标客户端时调整 WinHTTP 或应用专属代理。

修改前记录原值；不要默认执行全局代理重置。

### 修复 3：修复 DNS 状态

仅在解析证据异常时：

- 统一系统、浏览器和代理使用的 DNS 路径。
- 修复 Fake-IP 未接管或缓存陈旧问题。
- 避免浏览器安全 DNS 绕过必要的域名路由。
- 使用系统或网络工具提供的缓存刷新功能。

刷新 DNS 缓存不是长期修复；必须继续修复导致陈旧状态的配置。

### 修复 4：处理 IPv6 或 QUIC

仅针对已证明失败的协议路径进行最小调整。优先修复接管配置或对 OpenAI 流量回退 TCP 443，不全局关闭协议。

### 修复 5：处理 TLS 检查

个人设备上，确认是安全软件或本地网关造成替代证书时，只对 OpenAI 公共域名进行最小范围例外，并保留安全软件其他保护。

受管设备上，不自行绕过；提供证书颁发者、错误时间、目标域名和官方网络要求给管理员。

### 修复 6：清理单客户端状态

仅在网络层稳定、问题已限定到单客户端后：

- 浏览器：清除相关站点数据或移除冲突扩展。
- 桌面端：备份后重命名缓存子目录。
- 不删除整个用户配置目录。

### 修复 7：重置系统网络栈

最后手段。只有存在 Winsock、LSP、网络扩展或系统协议栈异常证据时才考虑。

执行前必须：

- 说明管理员权限和重启影响。
- 记录当前网络配置。
- 提供回滚或恢复步骤。
- 获得用户明确同意。

## 稳定性验证

修复后必须完成：

1. 运行连接测试至少 10 轮。
2. 记录 DNS、TCP、TLS、HTTP 状态和耗时。
3. 网页端普通窗口打开 ChatGPT。
4. 网页端发送消息并确认流式输出完成。
5. 桌面端打开 ChatGPT。
6. 桌面端发送消息并确认流式输出完成。
7. 关闭并重新打开两个客户端，不重启网络工具。
8. 在一次空闲期后再次发送消息，验证长连接不会因状态陈旧而失败。
9. 在用户原本容易复现的场景下复测。

成功标准：

- 多轮测试无 DNS、TCP、TLS 或代理隧道失败。
- 网页端和桌面端均可稳定打开和发送消息。
- 不需要刷新、切换出口、断开重连或重启网络软件。
- WebSocket 不出现持续握手失败或短时间反复断开。
- 所有关键 OpenAI 域名使用预期且一致的路径。

## 最终输出格式

### 1. 结论

用一到三句话说明已确认根因；未完全确认时写明“当前最可能根因”和置信度。

### 2. 关键证据

仅列最能区分根因的结果，不倾倒完整日志。

### 3. 已执行改动

逐项列出：

- 设置、文件或应用项。
- 修改前的安全摘要。
- 修改后的安全摘要。
- 备份位置或原值记录。

### 4. 验证结果

列出多轮成功率、网页端、桌面端、WebSocket 和是否仍需重启网络工具。

### 5. 回滚方法

## 禁止事项

- 不输出代理凭据、订阅 URL、节点密钥、Cookie、令牌或认证头。
- 不递归打印未知网络工具的完整配置目录。
- 不删除整个浏览器配置、应用数据或网络工具目录。
- 不全局关闭防火墙、杀毒软件、TLS 验证或组织安全策略。
- 不向 hosts 写入 OpenAI 固定 IP。
- 不默认关闭 IPv6、QUIC 或系统代理。
- 不一次执行多个不可逆网络重置。
- 不因其他网站正常就断言网络路径完全正常。
- 不把一次成功加载页面当作稳定修复。
- 不建议频繁切换出口或重启网络软件作为长期方案。

## 触发示例

应触发：

- “ChatGPT 网页端一直转圈，但其他网站正常。”
- “桌面端打不开，网页端偶尔可以。”
- “ChatGPT 提示 WebSocket 或网络连接错误。”
- “检查系统代理、DNS、证书和 IPv6 为什么只影响 ChatGPT。”
- “重新连接网络后暂时恢复，帮我找根因。”

不应触发：

- “ChatGPT Plus 如何退款。”
- “OpenAI API 返回 400。”
- “账号为什么被停用。”
- “帮我绕过公司网络限制。”
